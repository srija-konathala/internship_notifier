# internship job notifier

Polls ~250 job boards, remembers what it has already seen in SQLite, and sends
new internship matches to Telegram. It watches both the US and the UK, and it
discovers new London startups on its own.

```
main.py                        poll every board, filter, notify
config.json                    curated sources (generated by scripts/build_config.py)
config.uk.auto.json            sources discovered automatically (generated, safe to prune)
data/uk_seed_companies.json    hand-curated London startups to chase
data/uk_startups.json          discovery registry: scores, history, why a company failed
scripts/build_config.py        writes config.json
scripts/uk_sources.py          UK boards + the keyword/role profiles
scripts/discover_uk_startups.py  finds London startups and adds their boards
scripts/uk_ats_resolve.py      company -> job board resolver
scripts/verify_sources.py      re-check that configured boards still work
```

## Running it

```bash
pip install -r requirements.txt
playwright install --with-deps chromium     # only needed for playwright sources
cp .env.example .env                        # fill in TELEGRAM_BOT_TOKEN / TELEGRAM_CHAT_ID
python main.py --once                       # single pass
python main.py                              # loop forever
```

GitHub Actions runs `main.py --once` every 30 minutes
([watch.yml](.github/workflows/watch.yml)) and the London startup discovery once
a day ([discover-uk.yml](.github/workflows/discover-uk.yml)).

## Regions

`location_filter.countries` accepts `US` and `GB` (or `UK`, `USA`). A posting
matches if it looks like it is in any configured country. Location is a
heuristic over whatever the board gives us — country codes first, then location
strings, with guards so "London, Ontario" and "Cambridge, MA" do not count as UK.

Per-source overrides:

| field | effect |
| --- | --- |
| `"countries": ["GB"]` | only this country, regardless of the global filter |
| `"skip_location_filter": true` | accept every posting (for boards that publish no location, e.g. QinetiQ's RSS) |

44 US employers with London offices (Palantir, Stripe, Figma, Jane Street, Jump
Trading, Barclays, Google, Amazon...) are tagged `["US", "GB"]`, so their UK
internships now come through as well.

## What counts as a match

Two gates. First the title must contain an early-career keyword; then, unless
the source allows vague titles, it must also mention a relevant function.

Keyword profiles (`keyword_profiles` in config):

- default — `intern`, `internship`, `student`
- `uk_early_career` — adds the UK vocabulary: `placement`, `industrial placement`,
  `year in industry`, `summer analyst`, `spring week`, `graduate scheme`
- `startup_early_career` — adds `junior`, `new grad`, `entry level`, `associate`

Role profiles (`role_profiles` in config):

- `default` — software/CS titles only
- `uk_technical` — software plus engineering, data, quant, cyber, analytics; used
  for large UK employers whose placement schemes span every function
- `startup` — software plus product, growth, ops, design, business, and
  `allow_vague: true`, which lets through titles that name no function at all
  (a startup's "Operations Associate" or "Founder's Associate"). Seniority words
  (`senior`, `head of`, `principal`, ...) are excluded so "Tax Senior Associate"
  does not slip in.

A source picks profiles with `"keyword_profile"` and `"role_profile"`.

## Source types

`greenhouse`, `lever`, `ashby`, `smartrecruiters`, `workday`, `workable`,
`recruitee`, `pinpoint`, `teamtailor`, `phenom`, `avature`, `successfactors`,
`oracle_careers`, `pcsx`/`eightfold`, `google_careers`, `amazon`, `usajobs`,
`bofa`, `valve`, `adzuna`, `reed`, and `playwright` for sites that need a
browser.

`adzuna` and `reed` are UK-wide aggregators and need free API keys
([Adzuna](https://developer.adzuna.com/), [Reed](https://www.reed.co.uk/developers)).
Without the keys those sources skip themselves and everything else still runs.

## Adding sources

Curated sources live in Python, not in `config.json` directly:

```bash
# edit scripts/uk_sources.py (UK) or scripts/build_config.py (everything else)
python scripts/build_config.py       # regenerates config.json
python scripts/verify_sources.py --region uk --failing-only
```

`config.uk.auto.json` is never touched by the generator, so discovered startups
survive a regeneration.

## Discovering London startups

```bash
python scripts/discover_uk_startups.py                        # full run
python scripts/discover_uk_startups.py --dry-run --limit 40   # look, don't write
python scripts/discover_uk_startups.py --rank 25              # leaderboard
python scripts/discover_uk_startups.py --company Suna --domain suna.health
```

Candidates come from the YC open dataset filtered to London, London VC portfolio
pages (Seedcamp, Octopus, Concept, Hoxton), and
[data/uk_seed_companies.json](data/uk_seed_companies.json) — drop a name in that
file when you hear about a company and the next run chases it.

Each candidate is resolved to a real board by scanning its careers page for an
embedded board URL, then guessing slugs from the name, then rendering the page
with Playwright (`--render`) and watching for board API calls. A board is only
accepted once it returns live UK postings — that check is what caught that
Ashby's `tilthq` board is an unrelated US fintech while London's Tilt is `tilt`.

Accepted boards are scored 0-100 on free signals: YC or VC backing, batch
recency, stage, team size, open-role count, **hiring velocity** (change in open
roles since the last run), engineering share, and whether they post early-career
roles at all. Anything above `--min-score` is appended to `config.uk.auto.json`,
capped at `--max-add` per run. Everything else — including companies with no
resolvable board, like Suna, which hand-rolls its careers page — stays in
`data/uk_startups.json` and is retried oldest-first on later runs.

## No alert floods

A source with no history records its current postings silently and sends one
summary line ("Now watching 13 new sources"). Only postings that appear *after*
a source is being watched trigger an alert, so adding 60 boards at once does not
produce 60 messages. State lives in `state.db` (`seen_jobs` and `source_state`).

`source_state` is what tells a genuinely new board apart from a long-watched
board that has simply never matched anything. When you bulk-add sources, seed it
from the previous config first so the old ones keep alerting normally:

```bash
git show <commit-before-the-additions>:config.json > /tmp/old-config.json
python scripts/bootstrap_source_state.py --config /tmp/old-config.json
```

## Customizing

- Poll interval: `poll_interval_seconds`
- Concurrency: `fetch_workers` (playwright sources always run serially)
- Disable priming: `"prime_new_sources": false`
- Bound a slow Workday board: `"max_results": 400`
